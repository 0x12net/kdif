# kdif as a KiCad PCM package (`PCM/`)

How `plugin/` is turned into an archive KiCad's **Plugin and Content Manager**
(PCM) can install, how that archive is published from a git tag, and how the
self-hosted PCM repository that offers updates works. The command-line tool is
unaffected by everything here — it stays installable from the `.deb`, from
pip, or straight out of a checkout (see the root `README.md`).

Everything in this directory is plain Python with no third-party imports, so
the package can be built on Linux, macOS and Windows alike — the release
pipeline builds it on Linux, and CI (`.github/workflows/tests.yml`) builds it
on all three on every push.

## Why the archive is more than `zip -r plugin/`

PCM extracts **this archive and nothing else** onto the user's machine: there
is no repository checkout next to it, so anything `plugin/panel.py` imports at
runtime has to travel inside the zip. `panel.py` runs `python -m kdif` as a
subprocess, which means the whole `kdif` package must be bundled — cheap here,
since kdif is stdlib-only (a handful of `.py` files plus the HTML template).

`panel.py`'s `_plugin_root()` knows both layouts:

- **PCM install** — `kdif/` sits directly next to `panel.py`, exactly where
  `create_pcm_archive.py` put it.
- **Dev checkout** — `plugin/` is a sibling of `kdif/` (typically symlinked
  into KiCad's plugin directory, see `plugin/README.md`), one level up.

It checks the packaged layout first, since that is what end users have.

## Archive structure

```
kdif_<version>.zip
├── metadata.json               # generated from metadata.template.json
├── resources/
│   └── icon.png                # 64x64, optional; shown after download
└── plugins/
    └── kdif/
        ├── plugin.json         # IPC plugin manifest for KiCad
        ├── panel.py            # entrypoint (collects options, runs kdif)
        ├── requirements.txt    # kicad-python; the plugin venv installs it
        ├── icons/              # toolbar button, 24 and 48 px
        └── kdif/               # the tool itself, incl. template/viewer.html
```

## Building it locally

```bash
python3 PCM/create_pcm_archive.py v1.0.0     # -> PCM/kdif_v1.0.0.zip
python3 PCM/check_archive.py PCM/kdif_v1.0.0.zip
```

(or `make pcm`, which runs both with the version from `kdif/__init__.py`).

The build prints `download_sha256` / `download_size` / `download_url` /
`install_size` — the four values a `packages.json` entry needs. It is
idempotent: `PCM/archive/` and `PCM/*.zip` are wiped on every run, and the zip
is written with fixed entry timestamps, so rebuilding the same commit gives a
byte-identical archive with the same sha256.

`check_archive.py` is the guard against the class of mistake that only shows
up in a dialog on the user's machine: a `license` or `status` value outside
the PCM schema's closed enums, a `version` that kept its leading `v`,
`download_*` fields left inside the archive, a missing bundled module, a
`plugin.json` pointing at an icon that was never packaged.

**Install it by hand to try it out**: KiCad → *Plugin and Content Manager* →
*Install from File...* → pick the zip.

## How CI publishes a release

`.github/workflows/release-kicad-pcm.yml` runs on a `vX.Y.Z` tag:

1. `build_archive` — builds the archive with the same script as above,
   validates it, and attaches it to the GitHub release of that tag
   (`softprops/action-gh-release`, which creates the release if the `.deb`
   workflow has not already).
2. `publish_repository` — refreshes the self-hosted repository index (below)
   with the sha256/size/URL the first job computed and passed on as job
   outputs.

The tag is used verbatim for the release, the zip filename and the download
URL. A leading `v` is stripped only where the value lands in a PCM `version`
field, whose schema pattern permits digits and dots alone (`v1.2.3` fails
validation there) — `create_pcm_archive.py`'s `strip_v()` and
`pcm_repository.py` both do this.

The tag is also the *only* place a release number is written down. `kdif/__init__.py`
holds a `0.0.0` placeholder in git, and the workflow's first step replaces it
with the tag (`packaging/set_version.py`) before the archive is built — the
bundled `kdif/` is a source copy, so that is what `kdif --version` and the
plugin panel report on the user's machine.

Nothing here is hardcoded to this fork: `GITHUB_REPOSITORY` (set by Actions)
overrides the `0x12net/kdif` default in both scripts, so a fork publishes its
own URLs untouched.

## Self-hosted PCM repository

`pcm-repository/packages.json`, `repository.json` and `resources.zip` are
generated by `PCM/pcm_repository.py`. They are **not** committed to git —
they live as assets on a rolling GitHub release with the fixed tag
`pcm-repository`, which the workflow re-uploads (`gh release upload
--clobber`) on every tag push. That keeps generated files out of the
repository's history and keeps Actions from having to push to `main`.

Because a release asset is overwritten rather than merged, and `packages.json`
has to accumulate every released version (PCM offers users an upgrade path
from whatever they have installed), the workflow downloads the currently
published `packages.json` first and lets `pcm_repository.py` merge the new
version into it.

`resources.zip` is a different thing from the `resources/icon.png` *inside*
the archive: the in-archive copy is only seen once a package has been
downloaded, while the PCM browse list reads icons from the repository-level
`resources.zip` that `repository.json`'s own `"resources"` entry points at.
Without it, the package shows up in the list with no icon and no error. It is
rebuilt from `PCM/icon.png` on every run.

**Adding the repository in KiCad** (once per machine):

1. *Plugin and Content Manager* → **Manage...**
2. **+**, paste
   `https://github.com/0x12net/kdif/releases/download/pcm-repository/repository.json`,
   OK.
3. Close the dialog, pick the repository in the drop-down at the top.
4. **Apply Pending Changes** — installs the current version.

After that, updates are ordinary PCM updates: each new `vX.Y.Z` tag appears
there by itself once the workflow finishes. The `pcm-repository` release is
created automatically on the first tag push; there is nothing to set up by
hand.

**Do not hand-edit `pcm-repository/*.json`** — they are regenerated in full on
every release. To change the package's description, icon or license, edit
`PCM/metadata.template.json`; those fields are re-copied into `packages.json`
on the next tag (see `_upsert_package_version()`).

To preview locally exactly what CI would publish:

```bash
python3 PCM/create_pcm_archive.py v1.0.0        # prints the four values below
# optional, to reproduce a merge rather than a first publish:
gh release download pcm-repository --pattern packages.json --dir pcm-repository
python3 PCM/pcm_repository.py \
  --version v1.0.0 \
  --download-sha256 <from the output above> \
  --download-size <...> --download-url <...> --install-size <...>
```

**One caveat about the repository format**: KiCad 10 can serve different files
to different client versions through the `Accept` header
(`application/vnd.kicad.pcm.v2+json`). Static hosting — GitHub release assets
included — cannot vary a response by request header, so what is published here
is the v1 layout, which is both what header-less clients get and what other
third-party repositories use in practice. Honest v1/v2 duality would need a
small HTTP server rather than static files.

## The official KiCad repository

Getting listed in the repository every KiCad user sees out of the box goes
through **GitLab**, not GitHub: a merge request against
`https://gitlab.com/kicad/addons/metadata`. (Changes to
`gitlab.com/kicad/addons/repository` are not accepted — that one is generated
from `metadata`.)

What is already in place for it:

1. A public repository with an issue tracker.
2. A reverse-DNS package identifier based on the code host —
   `com.github.0x12net.kdif`. Changing it after the first publication breaks
   updates for anyone who already installed the package.
3. An open-source license. Note that `"license"` in `metadata.json` is not a
   free-form string but a closed enum from the PCM schema; kdif's `MIT` is in
   it (this is what `check_archive.py` verifies).
4. `download_sha256` / `download_size` / `download_url` / `install_size`
   belong in the `metadata.json` submitted to `packages/`, **not** in the copy
   inside the archive — which is why the template carries them and the build
   strips them.

The MR itself adds `packages/com.github.0x12net.kdif/metadata.json` with those
download fields filled in for a specific release.

## Worth knowing

- **The repository name `0x12net/kdif` is assumed** in
  `metadata.template.json`, `create_pcm_archive.py`, `pcm_repository.py` and
  this file. If the project moves, change them together
  (`grep -rn "0x12net/kdif" .`) — or rely on `GITHUB_REPOSITORY` in CI.
- **`kicad_version: "9.0"`** in the template is the first KiCad release with
  the IPC plugin API this plugin uses. `status` stays `"development"` until
  the package has been installed and used through PCM on a real machine.
- **`plugin.json`'s `identifier`** (KiCad's internal plugin id, also the venv
  cache key) and `metadata.json`'s `identifier` (the public PCM package id)
  are separate fields that happen to share the value
  `com.github.0x12net.kdif` here.
- **Icons** (`PCM/icon.png`, `plugin/icons/kdif_*.png`) are generated by
  `PCM/make_icons.py` — rerun it after changing anything in that script.
