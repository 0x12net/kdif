# kdif as a KiCad plugin (`plugin/`)

Wraps the kdif command line in a KiCad **IPC plugin** (KiCad 9+): a toolbar
button in pcbnew/eeschema opens a small panel where the revisions and layers
are ticked and the HTML file is written — instead of switching to a terminal
and typing `kdif --commits 3 board.kicad_pro`. Nothing opens by itself; the
**Open result** button shows the finished file in the browser.

Nothing about the diff itself lives here. `panel.py` builds the very same
command line and runs `python -m kdif` as a subprocess, streaming its output
into the log box. That keeps a long export from freezing the wx event loop,
and keeps the plugin from being a second implementation that can drift from
the CLI.

For how this directory is packaged and published for KiCad's Plugin and
Content Manager, see [`../PCM/README.md`](../PCM/README.md).

## What it does

The panel asks for as little as possible — a plugin already knows most of it:

| | comes from |
| --- | --- |
| the project | KiCad, over the IPC API (the document open in pcbnew/eeschema) |
| the commits | the project's git repository — only commits that touched the board or the schematic, newest first, shown as short hash + date + subject + tag |
| the layers | the board file itself, in the viewer's stacking order |
| kicad-cli | autodetected, preferring the install matching the *running* KiCad's major version |

So the whole UI is two lists of checkboxes plus an output path. The two most
recent commits and all layers are ticked when it opens, which is exactly what
`kdif <project>` does from a terminal — pressing **Generate** straight away is
a valid workflow.

Files:

- `plugin.json` — the manifest (schema `https://go.kicad.org/api/schemas/v1`)
  with one action, `generate-diff` → `panel.py`, scoped to `pcb` and
  `schematic`, so the button shows up in pcbnew and (on KiCad versions that
  support the scope) eeschema.
- `panel.py` — the wxPython panel described above; **Generate** turns into
  **Cancel** while a diff runs, and the log box mirrors kdif's own output.
- `icons/` — the toolbar button, 24 and 48 px, generated by
  `../PCM/make_icons.py`.
- `requirements.txt` — `kicad-python`, used for exactly one thing: asking the
  running KiCad what is open and which version it is. Without it the panel
  cannot identify the project and says so in its status line.

Options the CLI has and the panel deliberately does not: `--worktree`
(uncommitted state), `--check-zones`, `--show-fab-values`, `--kicad-cli`, `-j`.
They are one flag away in a terminal and would be one more thing to explain in
a toolbar dialog. `$KICAD_CLI` still overrides the autodetected kicad-cli for
both, and footprint values are left off the fab layers in both.

The panel is wxPython rather than Tkinter because KiCad creates the plugin's
venv with `--system-site-packages`: it inherits the wx that KiCad itself is
built on, while `python3-tk` is generally not installed.

## Requirements

- **KiCad ≥ 9** with *Preferences → Plugins → Enable KiCad API* turned on
  (that is what makes the toolbar button appear at all).
- **kicad-cli** — part of every KiCad install; nothing to configure. It is not
  on `PATH` on Windows or macOS, so kdif looks through the standard install
  locations, preferring the version of the KiCad that is running (an older
  kicad-cli cannot read a newer version's files). Whatever it resolved is
  printed in the log when the panel opens; `$KICAD_CLI` overrides it.
- **git**, and a project that lives in a git repository. On Windows that means
  Git for Windows; kdif's error message from the panel will say so if it is
  missing.

The panel compares **committed** revisions, so nothing needs saving in KiCad
first — the diff is between what git already has.

## Local development

Symlink this directory into KiCad's user plugin directory, so edits take
effect without repackaging. The path pattern is
`<KiCad user data dir>/<version>/plugins/<name>` (the sibling
`3rdparty/plugins/` is where PCM installs packages — leave that one to PCM):

```bash
# flatpak KiCad (check the version directory: ls ~/.var/app/org.kicad.KiCad/data/kicad/)
ln -s "$PWD/plugin" ~/.var/app/org.kicad.KiCad/data/kicad/10.0/plugins/kdif
# distribution KiCad
ln -s "$PWD/plugin" ~/.local/share/kicad/9.0/plugins/kdif
# macOS
ln -s "$PWD/plugin" ~/"Library/Application Support/kicad/9.0/plugins/kdif"
```

On Windows, either use a directory junction (`mklink /J
%APPDATA%\kicad\9.0\plugins\kdif <checkout>\plugin`, from an elevated prompt)
or just build and install the PCM archive.

Restart KiCad afterwards — or, if the plugin's venv already exists and
`requirements.txt` changed, *Preferences → Plugins*, right-click the action,
*Recreate Plugin Environment*. If the button does not show up on the toolbar,
enable it through the toolbar customization dialog.

`panel.py` finds the `kdif` package one level up in this layout, and inside
its own directory when installed from a PCM archive — see `_plugin_root()`.
`Path.resolve()` follows the symlink, so both work.

Inside the flatpak sandbox everything kdif needs is present: `git`,
`/app/bin/kicad-cli` on `PATH`, and `xdg-open` behind the *Open result* button.
Temporary files land in the sandbox's own cache
(`~/.var/app/org.kicad.KiCad/cache/kdif`), which is exactly where kicad-cli
running in that same sandbox can read them.

The panel keeps no state of its own between runs — everything it shows is
re-read from KiCad, git and the board file each time it opens.
